# Лабораторная 2: радиоуглеродное датирование

Тема 19: типы органических останков. Текущая лабораторная работает с останками,
исследователями и лайками. Заявки и вычисление календарной даты относятся к следующим
лабораторным и здесь не реализованы.

Приоритет имеет [актуальное задание](https://github.com/iu5git/Web#лабораторная-2).
[Методичка FastAPI](https://github.com/iu5git/Web/blob/main/tutorials/lab2-fastapi/README.md)
показывает технические приёмы, но её пример с отелями не полностью совпадает с заданием:
в нашем приложении три статуса вместо `is_deleted`, шесть обработчиков, нет изменения
лайков через интерфейс. Упоминание «удаления заявки» в задании трактуется как удаление
останков: таблицы заявок во второй лабораторной нет.

## Запуск

1. Активировать окружение: `source radiocarbon_dating_webapp/bin/activate`.
2. Установить зависимости: `python -m pip install -r requirements.txt`.
3. Заполнить `.env` по `.env.example`. Для приложения на компьютере адрес БД:
   `localhost:5434`. Логин и пароль должны совпадать с `docker-compose.yml`.
4. Запустить `docker compose up -d`. Не выполнять `docker compose down -v`:
   эта команда удаляет тома с БД и MinIO.
5. Применить миграцию: `python -m alembic upgrade head`.
6. Войти в [Adminer](http://localhost:8081): система PostgreSQL, сервер `postgres`,
   пользователь `user`, пароль из Compose, база `radiocarbon_db`.
7. Для первого наполнения выполнить содержимое `db/seed.sql` в разделе «SQL-запрос».
   Скрипт добавляет 31 исследователя, 5 записей останков и 65 лайков. На данном
   компьютере это уже выполнено через Adminer. Повторный запуск не перезаписывает
   существующие записи; он не предназначен для сброса внесённых изменений.
8. Запустить `python main.py`, открыть http://127.0.0.1:8000/remains.

Если окружения ещё нет: `python3 -m venv radiocarbon_dating_webapp`, затем шаг 1.
Пароли в Compose и `.env.example` предназначены только для локальной учебной работы.
`.env` исключён из Git. Другие локальные базы PostgreSQL проект не использует.

## Таблицы и ограничения

Три предметные таблицы: `researchers`, `remains`, `remains_likes`.
`alembic_version` — служебная таблица версии миграции, не четвёртая предметная модель.
Типы, длины, PK, FK и связи находятся в `radiocarbon.mdj`, который открывается в StarUML.
Статический просмотр той же схемы: `er.svg`.

- `researchers`: ID, уникальный логин до 80 символов, полное имя до 160 символов.
- `remains`: ID; название до 120 символов; описание до 2000; статус до 16;
  отдельные URL фото и видео до 1024; `analysis_time_days` — целое число рабочих дней;
  `carbon_14_pmc` — NUMERIC(7,3); дата создания; создатель FK; дата публикации.
  Поля `carbon_14_sample` (160) и `carbon_14_source` (1024) фиксируют источник
  опубликованного измерения C-14 для начальных данных.
- `remains_likes`: собственный PK и два FK: `researcher_id`, `remains_id`.
  Пара FK уникальна: один исследователь не может дважды отметить одну запись.
- Статусы: `draft`, `published`, `deleted`. Каскадного удаления нет,
  все внешние ключи имеют `ON DELETE RESTRICT`.
- Частичный уникальный индекс `uq_remains_creator_draft` запрещает два черновика
  одного исследователя даже при одновременных запросах.
- `created_at` и `published_at` — TIMESTAMP WITH TIME ZONE. Первая дата заполняется
  при INSERT, вторая сервером при публикации. Клиент эти поля не задаёт.
- В черновике описание и параметры могут быть NULL. Публикация требует описание,
  положительное время анализа, C-14 от 0 до 200 pMC и дату публикации.
- Приложение дополнительно ограничивает время анализа 36500 днями, точность C-14
  тремя знаками после запятой и проверяет длины строк.

## Шесть обработчиков

| Метод | Адрес | Реализация |
| --- | --- | --- |
| GET | `/remains?carbon_min=30` | ORM SELECT опубликованных останков с C-14 >= 30 |
| GET | `/remains/feed?remains_id=2` | ORM SELECT опубликованной записи и COUNT лайков |
| GET | `/remains/draft` | ORM SELECT черновика исследователя 999, без создания записи |
| POST | `/remains/draft` | ORM INSERT черновика с названием, кнопка «Далее» |
| POST | `/remains/{remains_id}/publish` | ORM UPDATE своего черновика и дата публикации |
| POST | `/remains/{remains_id}/delete` | Параметризованный SQL UPDATE через курсор psycopg |

`next=true` в ленте выбирает минимальный опубликованный ID больше текущего.
В конце выполняется переход к минимальному опубликованному ID. При ID 1, 9, 10
порядок будет 1 → 9 → 10 → 1. При отсутствии опубликованных записей показывается 404.
По URL черновика, удалённой или несуществующей записи ленты также возвращается 404.

Все успешные POST завершаются перенаправлением 303: обновление страницы не повторяет
добавление. Публикация блокирует строку `FOR UPDATE`, чтобы не опубликовать её повторно
двумя запросами. Повторный POST создания возвращает уже имеющийся черновик.
Чтение и поиск, создание и публикация используют ORM. Только удаление использует
`psycopg.AsyncConnection`, `connection.cursor()`, `cursor.execute()` и SQL `UPDATE`.
Параметры передаются отдельно от SQL, не подставляются строковой интерполяцией.

## Форма и файлы

При первом открытии без черновика отображаются название и поля фото/видео с кнопкой
«Далее». После создания или при уже существующем черновике появляются описание,
числовые поля и кнопка «Опубликовать». Некорректный ввод не меняет БД и возвращает
форму с ошибками и введёнными значениями. Название можно исправить до публикации.

Фото и видео из первой лабораторной остаются в MinIO. Новые file-input и URL-поля
находятся вне POST-формы и не имеют `name`: браузер не отправляет их ни в multipart,
ни в URL-encoded запросе. Сервер принимает только текстовые и числовые поля.
Новые записи получают NULL в `image_url`, `video_url`. Выбор локального файла
показывает его имя; без JavaScript он не подменяет предпросмотр. Обновление страницы
сбрасывает несохранённый выбор. Загрузок файлов и записи в MinIO в этой лабе нет.

В `static/images/default.jpg` и `static/videos/default.mp4` находятся локальные копии
иллюстраций древесины из первой лабораторной. Они показываются для новых записей,
NULL/пустых URL, ошибок или недоступности MinIO. Иконки также находятся на SSR-сервере,
в `static/icons`. Проверка доступности выполняется перед формированием HTML, без JS.
Видео имеет собственный URL, картинка не подставляется вместо него.

Для защиты от произвольных серверных запросов проверяются только URL внутри бакета,
заданного `MINIO_URL`; переходы на другие адреса не выполняются. Недоверенные адреса
тоже заменяются заглушками. Проверяется HTTP-ответ и тип файла; повреждённый файл,
который MinIO отдаёт с кодом 200 и верным Content-Type, требует замены в хранилище.

Лайки только выводятся через COUNT строк в БД; интерактивных checkbox и POST лайков нет.
Размер макета фиксированный 440 × 956 px, адаптивные перестроения не добавлены.
Динамическая подпись слайдера работает на CSS в поддерживающих view timeline браузерах;
поиск выполняется только после кнопки «Найти».

## Проверка

```bash
python -m alembic current
python -m alembic check
python -m unittest tests.test_lab2 -v
```

Тесты создают отдельную БД `radiocarbon_test_*`, применяют миграцию, проверяют поведение
и удаляют только эту временную БД. Требуется право CREATEDB (у локального пользователя

Проверяются шесть маршрутов, границы фильтра, скрытие черновика/удалённых,

валидация, защита от публикации чужого черновика, конкурентное создание, SQL-удаление,
сохранение связанных лайков, изменения через БД, заглушки и ограничения схемы.

## Показ преподавателю

Перед изменениями запомнить ID демонстрационной записи. Для удаления через Adminer
лучше использовать специально созданную запись, а не стирать исходные иллюстрации.
SQL-команды ниже выполняются в Adminer, не в терминале Python.

| Скриншоты | Что показать |
| --- | --- |
| 1–2 | В Adminer изменить статус опубликованной записи на deleted; SELECT подтвердит, что строка осталась |
| 3–4 | Плитка и поиск по C-14, параметр `carbon_min` в GET |
| 5–6 | Удалить другую карточку кнопкой; открыть её прежний URL ленты и показать HTTP 404 |
| 7–8 | Если есть «Дерево»-черновик, сначала опубликовать его; открыть добавление, ввести название, нажать «Далее»; SELECT покажет draft |
| 9–10 | Заполнить описание, время и C-14, нажать «Опубликовать»; SELECT покажет published и published_at |
| 11–13 | Изменить параметры в Adminer, добавить/убрать строку лайка, обновить приложение; показать изменившиеся поля и COUNT |
| 14–16 | Три ORM-модели, типы полей, FK, уникальный индекс черновика, ER-диаграмма |
| 17–21 | Пять обработчиков через ORM и шестой с SQL-курсором в repository.py; объяснить поиск и изменение статусов |
| 22 | Для новой карточки в HTML Response показать `/static/images/default.jpg` и `/static/videos/default.mp4` |

Просмотр данных и количества лайков:

```sql
SELECT r.id, r.title, r.status, r.analysis_time_days, r.carbon_14_pmc,
       r.creator_id, r.created_at, r.published_at, COUNT(l.id) AS likes_count
FROM remains AS r
LEFT JOIN remains_likes AS l ON l.remains_id = r.id
GROUP BY r.id
ORDER BY r.id;
```

Изменение полей существующей опубликованной записи (выбрать свой ID вместо 1):

```sql
UPDATE remains SET analysis_time_days = 18 WHERE id = 1;
INSERT INTO remains_likes (researcher_id, remains_id)
VALUES (999, 1) ON CONFLICT DO NOTHING;
```

Возврат начального времени и удаление добавленного демонстрационного лайка:

```sql
UPDATE remains SET analysis_time_days = 14 WHERE id = 1;
DELETE FROM remains_likes WHERE researcher_id = 999 AND remains_id = 1;
```

Логическое удаление примера через Adminer (подставить ID созданной для показа записи):

```sql
UPDATE remains SET status = 'deleted' WHERE id = 6 AND status = 'published';
SELECT id, title, status FROM remains WHERE id = 6;
```

ID 6 приведён только как пример: PostgreSQL не гарантирует отсутствие пропусков ID.
После демонстрации можно оставить тестовую запись логически удалённой.

## Контрольные вопросы

- Реляционная БД хранит связанные таблицы со схемой и ограничениями. Документная
  хранит документы, key-value — пары ключ–значение, графовая — узлы и рёбра.
- SELECT читает, INSERT добавляет, UPDATE меняет, DELETE физически удаляет строки.
  CREATE/ALTER/DROP изменяют схему; COMMIT/ROLLBACK завершают или отменяют транзакцию.
- Курсор выполняет SQL и позволяет получать строки результата. В удалении курсор
  выполняет UPDATE ... RETURNING id; строка останков остаётся в таблице.
- ORM сопоставляет класс Python таблице, атрибуты — столбцам. SQLAlchemy строит SQL
  и управляет сессией/транзакцией, но не отменяет необходимости знать ограничения БД.
- Модель описывает текущую структуру. Миграция — версионированное изменение схемы,
  которое Alembic применяет через upgrade; служебная таблица хранит текущую версию.
- HTTP-слой принимает запрос и выбирает ответ; слой доступа к данным делает запросы;
  модели описывают сущности, шаблоны отвечают за представление. В проекте эти задачи
  разделены между api, data/db/models и templates, без помещения SQL в шаблоны.

## Источники данных и оформления

Содержание C-14 дано в pMC, не в процентах массы. Это опубликованные измерения
конкретных образцов, а не постоянные значения для всего типа останков. Фото являются
иллюстрациями типов материала, не фотографиями именно этих стандартов.

| Останки | Образец | pMC | Источник |
| --- | --- | --- | --- |
| Уголь | OxA X-2698-45 | 1.385 | [Higham et al., 2024, таблица 1](https://doi.org/10.1038/s41467-024-51546-9), fM × 100 |
| Кости | VIRI I, KIA 30536 | 34.45 | [Huels et al., таблица SIII](https://doi.org/10.13140/RG.2.1.4201.6248) |
| Ракушки | VIRI R | 73.338 | [Geochronometria, таблица 3](https://www.geochronometria.com/pdf-184439-105187?filename=Set-up--optimization-and-.pdf) |
| Дерево | IAEA-C5 | 23.05 | [МАГАТЭ](https://analytical-reference-materials.iaea.org/iaea-c-5) |
| Торф | FIRI M | 24.85 | [Huels et al., таблица SIII](https://doi.org/10.13140/RG.2.1.4201.6248) |

Срок исходных записей: до 14 рабочих дней стандартного AMS-анализа
([Beta Analytic](https://www.radiocarbon.com/carbon-dating-cost.htm)). При изменении
значения C-14 в форме публикации ссылка на прежнее измерение и его идентификатор
очищаются, чтобы не приписывать введённое число чужому образцу.

Сохранён hover кнопок radiocarbon.com: белый текст #ffffff, фон #025aa5,
рамка #01549b. Основные цвета макета: #316db2, #111927, #ffffff.
Иконка удаления — Lucide 0.468.0, лицензия в `static/icons/LICENSE-Lucide`.
